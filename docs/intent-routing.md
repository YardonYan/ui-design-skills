# 意图识别与自动匹配说明

这份文档回答一个问题：使用者只说`我要做一个产品`，AI 怎么判断该读仓库里的哪一个技能。

它同时是给人和给 AI 看的。人可以用它确认`我这类需求大概会被怎么理解`；AI 在读根 `SKILL.md` 之后，按这里的维度、映射和兜底规则做判断。使用者不需要读这份文档，也不需要知道任何技能名。

## 为什么需要

Vibe Coding 场景下，人的输入通常是一句话需求，例如`给我做一个记账 App 的首页``做个带审批的 AI 助手界面``这套图标不够统一，重做`。这类描述里不会出现技能名，也不该要求出现。

如果让人先查目录、再精确报出 `skills/web/saas-landing/SKILL.md`，等于把路由工作推回给使用者，既不符合实际习惯，也会让人卡在第一步。所以仓库把路由做成自己的职责：整个仓库作为一个 Skill 被调用，入口是根目录 `SKILL.md`，判断依据就是这份文档。

同一条原则适用于外部参考资料：仓库另收了 9 类资源链接与 5 家上游技能文本，但默认一律不加载。只有使用者明确要找资源、找灵感、借外部经验时才按 `docs/resource-routing.md` 读命中的一份。要的是产物就走技能，不要先翻清单。

## 四个意图维度

按顺序抽取，够用就停，不要为了凑齐四维去追问。

| 维度 | 要回答什么 | 典型信号 |
|---|---|---|
| 产物 | 最终要拿到什么 | 页面、界面、一屏 App、一组图标、一套配色、一份 Schema、一份问题清单、一张海报 |
| 载体 | 跑在哪里、给谁看 | 官网、落地页、管理端、后台、手机、小程序、对话窗口、文档站、印刷物 |
| 阶段 | 从零做，还是改已有东西 | 从零、做个原型、照着这个改、一眼 AI 味、审一下、验收、导出、复刻 |
| 约束 | 有没有硬性限制 | 技术栈、单文件、无外部依赖、桌面 1440、移动端、深色浅色、字段清单、不要渐变 |

产物维度权重最高。产物判断不出来时，先按载体猜一个，再在交付前用一句话确认，不要停下来等答复。

## 六类与首选技能

| 类别 | 什么时候进 | 首选 | 备选 | 常一起用 |
|---|---|---|---|---|
| `web` | 面向公众的网页、页面类型、还原与原型 | `saas-landing` | `pricing-page`、`docs-page`、`faq-page`、`web-clone` | `web-design-guidelines` |
| `enterprise` | 中后台、字段、表单、信息架构、看板 | `enterprise-admin` | `admin-form-schema`、`admin-ia-patterns`、`dashboard` | `frontend-spec` |
| `mobile` | App 单屏、引导页、多端尺寸 | `mobile-app` | `mobile-onboarding`、`mobile-design-spec` | `web-design-guidelines` |
| `components` | 组件、区块、图标、插画、图表、AI 对话组件 | `assistant-ui` 或 `icon-system`，按产物定 | `cult-ui`、`ricoui-blocks`、`spotkit`、`bootstrap` | `ai-chat-patterns` |
| `foundations` | 方向、配色、品牌、交互状态、整改与验收 | `oil-ui` 或 `unslop`，按阶段定 | `flexoki-palette`、`ai-chat-patterns`、`web-design-guidelines` | `review-animations` |
| `tooling` | 调试、转换、画布格式、交付链路 | `html-skill-effectiveness` 或 `chrome-devtools`，按产物定 | `html-to-pdf`、`json-canvas` | `web-design-guidelines` |

`components` 与 `foundations` 的首选需要二次判断：要`做出来的东西`进 `components`，要`判断、规范、状态或整改`进 `foundations`。

## 冲突裁决

| 冲突 | 裁决 |
|---|---|
| 像网页又像后台 | 有增删改查、字段、权限、列表详情，走 `enterprise`；只有展示与转化，走 `web` |
| 像组件又像整页 | 要一整页走页面类技能，只要一个可复用块走组件类技能 |
| 既要图标又要配色 | 按产物一次性给：图标为主走 `icon-system`，配色为辅带 `flexoki-palette` |
| 从零做 + 整改同时出现 | 先整改（有现成东西），整改完再谈从零；不要同时开两条线 |
| AI 对话界面 + 状态清单 | `assistant-ui` 主、`ai-chat-patterns` 辅，先列状态再落地组件 |
| 使用者点名了技能 | 尊重指定，但仍读该技能的 `SKILL.md` 确认边界；边界不符时说明并给替代 |
| 使用者描述里有内部字段名 | 只用给出的字段，不臆造；需要外部检索时把字段名抽象化 |
| 既要产物又要找资源 | 先按产物走技能，产出后再按 `docs/resource-routing.md` 补一份参考，不要先翻清单 |
| 想提升质感但不想换产物形态 | 主技能不变，额外调用一个整合技能，按它的 `SKILL.md` 取 1 到 3 份参考文件 |
| 分不清要网址还是要做法 | 要网址查资源索引，要规则调整合技能；仍分不清就只读资源索引的 `INDEX.md` 判断 |

## 兜底路径

判断不出来时按这个顺序走，任何一步能定下来就停。

1. 产物能不能归到六类之一？能 → 进对应类别的首选技能。
2. 产物判断不出，但能看出载体？网页按 `saas-landing` 起步，后台按 `enterprise-admin` 起步，手机按 `mobile-app` 起步，对话按 `assistant-ui` 起步。
3. 载体也看不出，但能看出阶段？整改走 `unslop`，验收走 `web-design-guidelines`，定方向走 `oil-ui`。
4. 四个维度都模糊 → 最多问两个问题：你要的是页面、界面还是文件？给谁用、在什么设备上看？不要连环追问，不要让用户看目录。
5. 仍然没有信息 → 用 `oil-ui` 给一个方向稿，再让用户挑，比空等更有用。
6. 产出明显不是界面（Word、PDF、PPT、后端接口、数据分析、运维） → 直接说明不在本仓库范围，不硬凑技能。
7. 四个维度都像`找东西`而不是`做东西` → 转 `docs/resource-routing.md`，只读命中的一份索引或智慧文件。

任何兜底路径下都不要做这三件事：不要要求用户报技能名，不要一次加载多个候选技能让上下文变重，不要为了`以防万一`预读资源索引。

## 多技能组合顺序

一个需求需要多个技能时，按做界面的主线排，不要反过来：

定方向 → 定结构或列状态 → 出稿 → 套类型 → 配素材 → 验收

| 需求 | 推荐顺序 |
|---|---|
| 全新的 AI 助手产品 | `oil-ui` → `ai-chat-patterns` → `assistant-ui` → `web-design-guidelines` |
| 中后台系统 | `admin-ia-patterns` → `admin-form-schema` → `enterprise-admin` → `frontend-spec` |
| 品牌官网 | `oil-ui` → `saas-landing` → `icon-system` → `flexoki-palette` → `unslop` |
| 移动端 App | `mobile-design-spec` → `mobile-app` → `spotkit` → `web-design-guidelines` |

组合里的辅助技能最多两个。超过两个说明需求该拆成几次对话，不要一次做完。

## 给 AI 的可执行判断清单

1. 读使用者描述，抽出产物、载体、阶段、约束，缺的不追问也能继续。
2. 判断这是`做东西`还是`找东西`。找东西 → 转 `docs/resource-routing.md`，结束本清单。
3. 判断产物是否属于界面。不是 → 说明不适用，结束。
4. 落到六类之一，选一个主技能。
5. 判断是否需要辅助技能，最多两个，按主线顺序排；需要外部规则时再加一个整合技能。
6. 读被选中技能的 `SKILL.md`，再按需读 `references/`、`templates/`；资源索引默认不读，命中才读。
7. 按技能规则产出，不要跳过规则自由发挥。
8. 交付时用一句话说明匹配了哪几个技能和理由。
9. 使用者反馈不对，就换一个技能重做，不要辩论路由结果。

## 反例

| 不要这样 | 应该这样 |
|---|---|
| 请问您想用 `saas-landing` 还是 `pricing-page` | 直接判断并给出产物，末尾一句话说明用了哪个 |
| 请先查看 `ROUTER.md` 选择技能 | 使用者不需要看目录，路由是仓库的职责 |
| 您没说技能名，我无法开始 | 按兜底路径起步，最多问两个澄清问题 |
| 一次性读 78 个 SKILL.md 确保不漏 | 只读选中的 1 到 3 个 |
| 描述里没提字段，我补了几个常见的 | 只用给出的字段，不臆造 |
| 把内部系统名写进外部检索的查询词 | 用抽象描述，真实信息本地再填 |
| 先把 140 条资源链接和 169 份外部智慧读一遍 | 默认不读；命中才读一份，最多三份 |
| 做落地页前先翻组件站找灵感 | 直接走页面技能，产出后再按需补素材 |

## 怎么验证匹配对不对

交付后看三点：产物形态对不对（页面 / 图标 / 清单）、载体对不对（桌面 / 后台 / 手机 / 对话）、有没有越过使用者给的约束。三点都对，路由就算对；产物形态不对时换主技能，不是改措辞。

## 维护

新增技能时，在根 `SKILL.md` 的快捷映射表、`ROUTER.md` 的口语索引、`docs/skill-map.md` 的清单和本文件的六类映射里各补一行。四份不一致时，以本文件的裁决规则为准。`docs/skill-map.md` 的清单由 `tools/build_index.py` 生成，不要手改。

新增资源链接或外部智慧来源时，改 `references/resources/SOURCE.md` 或对应来源目录的 `SOURCE.md`，然后跑 `tools/build_resource_index.py` 重算索引；加载规则同步更新根 `SKILL.md`、`docs/resource-routing.md` 与本文件，三处口径保持一致。
