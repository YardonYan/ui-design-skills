# 八个页面配方

每个配方给三样：骨架、必备部件、易错点。骨架是 ASCII，照着摆位置；部件名对应 `component-map.md` 里的 shadcn/ui 组件。

---

## 1. 列表页

后台里出现频率最高的一屏。判断标准：用户来这里是为了"从一堆记录里挑出几条"。

```
┌─────────────────────────────────────────────────┐
│ 页面标题            [次要动作] [主操作 新建]      │
├─────────────────────────────────────────────────┤
│ 查询区：关键词 · 状态 · 日期区间 · 归属    [更多筛选]│
├─────────────────────────────────────────────────┤
│ 已选 3 项  [批量导出][批量改状态][删除]  ← 条件出现 │
├─────────────────────────────────────────────────┤
│ ☐ 编号   名称        状态    金额    更新人  操作  │
│ ☐ ...                                            │
├─────────────────────────────────────────────────┤
│ 共 1,284 条   每页 20 ▾   ‹ 1 2 3 ... 65 ›       │
└─────────────────────────────────────────────────┘
```

必备部件：`DataTable` + `Toolbar` + `FacetedFilter` + `Pagination` + `BulkActions` + 空态 + 加载骨架。

规则：

- 查询状态全部进 URL。刷新后同一屏必须还原，分享链接给同事能打开同样的结果。
- 分页服务端做。返回体里带 `total`，别用数组长度当总数。
- 默认排序显式写出来，通常是 `updated_at desc`。没有默认排序的列表，翻页时会出现记录重复或丢失。
- 批量操作栏只在有选中项时出现，位置固定，不要挤进工具栏。
- 空态分两种文案：没有数据（引导新建）、筛选无结果（引导清空条件）。两种混用会让用户以为数据丢了。
- 行操作列不超过三个，超出收进 `⋯` 菜单。危险动作放最后并用红色。

易错点：把筛选做成前端过滤几百条缓存数据；把 total 算成当前页条数；分页切页时选中项被清空导致用户重复操作。

## 2. 详情页

判断标准：用户已经选定了某一条，现在要看清全貌并决定下一步做什么。

```
┌─────────────────────────────────────────────────┐
│ ‹ 返回列表   单号 SO-2026-0187   [状态徽章]  [主操作]│
│ 客户：某某公司 · 金额 ¥128,400 · 交期 11-20        │
├──────────────────────────────┬──────────────────┤
│ [基本信息][明细][关联单据][操作日志]                │
│                              │ 侧栏：            │
│  字段成对排布，标签在上值在下   │ 负责人 / 创建时间  │
│  长文本单独成段               │ 关联记录 3 条      │
│                              │ 附件 2 个         │
└──────────────────────────────┴──────────────────┘
```

必备部件：`Breadcrumb` + `Badge`（状态）+ `Tabs` + `Card`（侧栏）+ `Separator`。

规则：

- 首屏顶部三行内给结论：单号、对方、金额、状态、关键日期。用户不该滚动才知道这单是什么。
- 状态徽章的颜色固定映射，全站一致。见 `design-md-library` 取语义色，别每个页面自己定。
- 主操作跟随状态变化。草稿给"提交"，已提交给"审核"，已完成只给"打印/导出"。按钮不该出现点了报错的情况。
- 字段展示用 `描述列表`（标签 + 值两列），不要用只读输入框。只读输入框会让人以为能改。
- 右侧栏放元信息与关联，不放主内容。窄屏时侧栏折到下方。
- 关联记录只显示前 5 条 + 查看全部，别在主页面里嵌一个大表格。

易错点：把详情页做成一个大表单，用户分不清是看还是改；操作按钮放在页面最底部；状态没有可视化，只看文字。

## 3. 编辑页（新建与修改）

判断标准：要写入。新建和编辑共用一套表单，靠是否有 id 区分。

```
┌─────────────────────────────────────────────────┐
│ ‹ 返回   新建生产单             [取消] [保存草稿][提交]│
├─────────────────────────────────────────────────┤
│ ① 基本信息                                       │
│   客户 *[选择]  联系人[   ]  电话[   ]            │
│ ② 产品与工艺                                     │
│   材质 *[▾]  尺寸 *[  ]×[  ]  数量 *[  ]          │
│ ③ 交付                                           │
│   交期 *[日期]  送货地址[            ]            │
├─────────────────────────────────────────────────┤
│ 未保存的改动会在离开时提示                        │
└─────────────────────────────────────────────────┘
```

必备部件：`Form` + `FormField` + `Input` / `Select` / `DatePicker` + `ConfirmDialog`（离开拦截）+ `Toast`。

规则：

- 按业务动作分组，不按数据类型分组。"客户信息 / 产品与工艺 / 交付"是动作，"文本字段 / 数字字段"不是。
- 一组不超过 12 个字段，一页不超过 5 组。超了拆步骤或拆 Tab，别硬堆。
- 必填项标在标签后，不要只靠红色边框提示。
- 保存草稿与提交分开。草稿允许不完整，提交必须校验全。
- 离开前拦未保存。用路由守卫，不要只靠 `beforeunload`。
- 校验错误定位到字段，并在顶部给一条汇总（几个字段有问题），长表单里用户找不到红框。
- 联动字段（选了 A 才出现 B）用 `depends_on` 式条件渲染，值清空时要一并清掉依赖字段的数据。

易错点：编辑页用弹窗；所有字段都必填导致没人能保存；校验只在提交时做一次，用户改完不知道好了没。

## 4. 导入向导

判断标准：一次要进几十上百条，来源是对方的 Excel。这是企业后台最容易被做残、也最影响口碑的一屏。

```
第 1 步 上传
┌─────────────────────────────────────┐
│  拖入 .xlsx / .csv  或 [选择文件]     │
│  模板下载：生产单导入模板.xlsx         │
└─────────────────────────────────────┘

第 2 步 字段映射（列名对不上时出现）
┌─────────────────────────────────────┐
│ 表格列「客户名称」 → 系统字段 [客户 ▾] │
│ 表格列「交期」     → 系统字段 [交期 ▾] │
│ 未映射 2 列（忽略）                   │
└─────────────────────────────────────┘

第 3 步 预检报告
┌─────────────────────────────────────┐
│ 共 128 行 · 可入库 121 · 有问题 7      │
│ 第 14 行  数量为空        必填缺失     │
│ 第 37 行  材质「亚克力板」不在字典     │
│ 第 88 行  交期早于下单日   逻辑冲突     │
│           [下载问题清单] [返回修改] [忽略 7 行继续]│
└─────────────────────────────────────┘

第 4 步 结果回执
┌─────────────────────────────────────┐
│ 已入库 121 条 · 失败 0 · 耗时 4.2 秒  │
│ [查看导入记录] [下载回执]             │
└─────────────────────────────────────┘
```

必备部件：`Stepper`（四步，不可跳步）+ `FileDropzone` + `Select`（映射）+ `Table`（预检）+ `Alert`（问题分级）+ `Progress`。

规则：

- 四步必须分开，第 3 步是核心，绝不允许上传即入库。
- 预检报告要精确到行号和列名，并给出人话原因。"数据格式错误"这种提示等于没提示。
- 问题分两级：阻断（必填缺失、类型不符）与警告（字典不匹配、疑似重复）。警告允许忽略并入库，阻断不行。
- 提供模板下载。让用户自己猜列名是最常见的失败原因。
- 入库用事务，全成功或按行记录失败，不要一半成功一半静默丢。
- 结果回执给导入批次号，可回溯。以后出问题能定位是哪一次导入带进来的。
- 超过 500 行改异步，给进度条与后台任务，不要让用户盯着转圈。

易错点：一步到位静默入库；失败只报条数不报行号；重复导入不查重，同一张表导两遍变双份。

## 5. 权限矩阵

判断标准：管理员要配"谁能看谁能改"。别做成四个页面各配一遍。

```
┌──────────────────────────────────────────────────┐
│ 角色：业务员 ▾            [重置] [保存]            │
├──────────────────────────────────────────────────┤
│ 资源          查看  新建  编辑  删除  导出  审批    │
│ 生产单         ✓     ✓     ✓     ✗     ✓     ✗   │
│ 报价单         ✓     ✓     ✗     ✗     ✗     ✗   │
│ 客户资料       ✓     ✗     ✗     ✗     ✗     ✗   │
│ 系统设置       ✗     ✗     ✗     ✗     ✗     ✗   │
├──────────────────────────────────────────────────┤
│ 数据范围：☑ 仅本人  ☐ 本部门  ☐ 全部              │
└──────────────────────────────────────────────────┘
```

必备部件：`Select`（角色）+ `Table`（矩阵）+ `Switch` / `Checkbox`（格内）+ `Alert`（影响提示）。

规则：

- 三个维度：角色 × 资源 × 动作。动作固定一套：查看、新建、编辑、删除、导出、审批。别每个模块发明一套动词。
- 数据范围单独一行，管的是"能看到谁的记录"，与功能权限正交。
- 行内开关即改即生效前必须二次确认，并提示影响人数（该角色下 12 个用户）。
- 前端隐藏按钮只是体验，接口必须校验同一张表。这条在硬规矩里已写，这里再强调一次因为最常被跳过。
- 给一份"当前角色的实际权限预览"，管理员配完能立刻验证。

易错点：权限表写在代码里改一次发一次版；只做功能权限不做数据范围，导致业务员能看到全部客户；超级管理员硬编码进前端判断。

## 6. 审批流

判断标准：单据要人点头才能往下走。

```
┌──────────────────────────────────────────────────┐
│ 状态：待财务审核（第 2 / 3 步）                     │
├──────────────────────────────────────────────────┤
│ ● 提交        张三    11-08 09:12                │
│ │ 备注：客户催单，请优先                          │
│ ● 部门审核    李四    11-08 10:30  同意          │
│ │ 备注：已核对库存                                │
│ ◉ 财务审核    待处理   已等待 6 小时              │
│    [同意] [驳回]  ← 仅当前处理人可见              │
│ ○ 完成                                          │
└──────────────────────────────────────────────────┘
```

必备部件：`Timeline`（垂直）+ `Avatar` + `Badge`（节点状态）+ `Textarea`（意见）+ `AlertDialog`（驳回确认）。

规则：

- 状态机显式定义，节点顺序、会签或签、跳过条件都写进配置，不散在代码 if 里。
- 时间轴给四样：节点名、处理人、时间、意见。缺一个都会有人来问。
- 当前节点高亮，且只对当前处理人显示操作按钮。别人看到的是"等待某某处理"。
- 驳回必须填原因，且要能选择驳回上一节点还发起人。
- 同意与驳回都要二次确认，驳回的确认框里写清"将退回至发起人，已填内容保留"。
- 超时提醒：等待超过 N 小时给催办入口，别让人肉盯。

易错点：审批意见用 alert 弹出来；时间轴只显示"已通过"不显示人；驳回后单据直接作废而不是退回。

## 7. 字典与编号规则

判断标准：下拉选项和单号需要业务自己维护。这两件事放一起，因为都是"配置一次、全站生效"。

字典：

```
┌──────────────────────────────────────────┐
│ 字典：材质类型              [+ 新增项]     │
├──────────────────────────────────────────┤
│ 编码      名称        排序  启用   操作    │
│ M-AC     亚克力       10    ✓    编辑 删除│
│ M-ST     不锈钢       20    ✓    编辑 删除│
│ M-PVC    PVC板        30    ✗    编辑 删除│
└──────────────────────────────────────────┘
```

规则：字典项有稳定编码，名称可改编码不改，历史数据才不会失真；停用不做删除，停用项不出现在新建下拉里但历史记录照常显示。

编号规则：

```
前缀 [SO]  +  日期 [YYYYMM]  +  流水 [4 位]  →  SO202611-0187
```

规则：流水号按前缀 + 日期段独立计数；并发生成用数据库序列或行锁，不用 `count()+1`；允许手工改号但需唯一校验；单号一旦生成不可变。

易错点：下拉选项写死在组件里；删除字典项导致历史单据显示空白；单号用时间戳，看起来唯一其实会撞。

## 8. 主从表

判断标准：一张单据带多行明细，明细有自己的字段和小计。

```
┌────────────────────────────────────────────────────┐
│ 明细（7 行）                          [+ 添加一行]  │
├────┬──────────┬────┬──────┬────────┬──────┬───────┤
│ #  │ 产品     │数量│ 单价 │ 金额   │ 备注  │       │
│ 1  │ 门头招牌 │ 2  │ 1200 │ 2,400  │      │ 删除  │
│ 2  │ 灯箱     │ 1  │ 3800 │ 3,800  │ 加急  │ 删除  │
├────┴──────────┴────┴──────┴────────┴──────┴───────┤
│ 合计 7 行 · 数量 12 · 金额 ¥28,600（后端复算）      │
└────────────────────────────────────────────────────┘
```

必备部件：`Table`（可编辑行）+ `Input`（行内）+ `Button`（增删行）+ 底部汇总条。

规则：

- 行内编辑优先，别为改一行开弹窗。字段超过 8 个的明细行才考虑抽屉。
- 序号列自动维护，删行后重排。
- 金额 = 数量 × 单价，前端即时算给反馈，提交后以后端复算为准，差异要提示。
- 至少保留一行空行，删到零行时给"添加第一行"的引导。
- 明细可以拖拽排序时，排序值要落库，下次打开顺序一致。
- 主表未保存时明细行只存在前端，离开拦截要覆盖这种情况。

易错点：合计只在前端算，导出时对不上；明细行没有唯一 id，删中间行后数据错位；明细字段没做校验就提交。
