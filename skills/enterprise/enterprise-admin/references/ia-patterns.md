# 模块划分与命名

先切模块再写页面。切错了，后面的组件会长成两套。

## 三层导航

```
一级：模块      生产 / 销售 / 采购 / 库存 / 财务 / 设置
二级：列表页    生产单 / 工单 / 排产
三级：记录      某一张单的详情与编辑
```

一级不超过八个。超过八个说明按技术分层了，不是按业务分。一级超过八个的典型症状：用户找不到入口，全靠搜索。

## 模块分三类

| 类 | 是什么 | 例子 | 特点 |
|---|---|---|---|
| 业务域 | 直接产生价值的流程 | 报价、下单、生产、发货、对账 | 字段多、状态多、要审批 |
| 支撑域 | 业务域共同依赖 | 客户、物料、供应商、员工、附件 | 被引用多，变动少 |
| 配置域 | 管理员维护 | 字典、编号规则、权限、审批配置 | 低频高风险 |

配置域单独收在一处，不要散进业务菜单。管理员找得到，业务员看不见。

## 三种切法对照

同样一个 CRM，三种开源项目的切法差异很大，值得对看：

| 切法 | 代表 | 切分依据 | 适合 |
|---|---|---|---|
| 按业务对象 | twenty | 每个对象（公司/联系人/商机）一套列表详情 | 对象数量少、结构相似 |
| 按业务动作 | ERPNext | 报价 → 订单 → 发货 → 开票，按单据流转 | 流程长、单据间有严格先后 |
| 按使用角色 | ToolJet | 搭建态与使用态两个入口，两套界面 | 用户自己配应用给别人用 |

绝大多数企业后台是第二种：按单据流转切。判断方法：如果业务方说的是"先开单，再审核，然后发货"，就是流程型；如果说的是"我要看所有客户"、"我要看所有合同"，是对象型。

## 配置态与使用态要分开

ToolJet 的做法值得抄思路：搭应用的人看到 `AppBuilder`，用应用的人看到 `ViewerApp`，两套路由两套布局。

对应到自建后台：

- 配置态：字典、编号规则、审批流程、权限矩阵、字段自定义。低频，只在设置里。
- 使用态：列表、详情、编辑、导入。高频，占 95% 的操作。
- 两者的组件可以复用，路由和权限必须分开。混在一起的后果是业务员在列表页看到"配置字段"按钮。

## 什么时候用元数据驱动

twenty 的核心设计是字段定义存在数据库里，加字段不用改代码。代价是复杂度陡增：要写元数据解析、动态表单渲染、视图保存、迁移工具。

判断标准：

| 条件 | 结论 |
|---|---|
| 业务方经常自己加字段，一周一次以上 | 值得做元数据驱动 |
| 字段一年改两三次 | 不值得，改代码更快 |
| 一套系统要服务多个客户，字段各不同 | 必须做，否则维护成本爆炸 |
| 只有一家公司内部用 | 不做，把 Schema 写成 TypeScript 类型就够 |

先做静态 Schema（`field-schema.md` 那份 JSON 当配置文件），等真的撑不住了再上元数据驱动。反过来先上元数据的，多半死在调试期。

## 命名三处一致

同一个资源，路由、接口、权限键必须同名。这是后台项目最常见的长期债务。

```
资源：生产单
路由    /production-orders
接口    /api/production-orders
权限键  production_order:read
表名    production_order
组件    ProductionOrderTable
```

规则：

- 路由用复数连字符，接口同路由，表名单数下划线。三处能对上，靠的是词根一致而不是格式一致。
- 权限键 `资源:动作`，动作固定为 read / create / update / delete / export / approve 六个。
- 组件名用 `资源 + 部件`，如 `ProductionOrderTable`、`ProductionOrderForm`。别用 `Table1`、`ListComponent`。
- 中文名只在 label 里出现一次，代码里不出现拼音。拼音命名后期没人认得。

## 目录结构

按功能切，不按技术切。技术切法（components / hooks / utils / services）在页面超过二十个后会失效，改一个功能要在四个目录里跳。

```
src/
  features/
    production-orders/
      api.ts            # 请求与类型
      schema.ts         # 字段定义
      columns.tsx       # 列表列定义
      table.tsx         # 列表页
      detail.tsx        # 详情页
      form.tsx          # 编辑页
      import-wizard.tsx # 导入（有才建）
    customers/
    settings/
  components/           # 跨功能复用的部件
  lib/                  # 工具
```

shadcn-admin 就是这么组织的：`src/features/` 下按业务切 auth / dashboard / users / tasks / apps / chats / settings / errors，通用部件留在 `src/components/`。照着这个切，新人进来找功能按名字找就行。

## 路由与权限的对应

每个路由声明自己需要的权限键，由路由层统一拦截，不在页面里写判断：

```ts
{ path: '/production-orders', component: OrderList, permission: 'production_order:read' }
{ path: '/production-orders/new', component: OrderForm, permission: 'production_order:create' }
```

好处是加页面时只加一行声明，漏配权限会被路由层直接挡掉，不依赖开发记得写 `if`。

## 导航排序

按使用频率排，不按字母排，也不按业务流排。用户一天点二十次的东西放第一个。判定方法：问业务方"你上班第一件事点哪里"。
